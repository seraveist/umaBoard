## P1: 후반 오르막 영역

[현재 조건 판정](../assets/activation.mjs)의 후반 오르막은 각 경사의
`start + length/2`부터 끝까지를 고른다. 그러나 고정한
[umasim 조건 구현](https://github.com/mee1080/umasim/blob/e9bb2939ba117ea93e556790c353ed3edec27eab/race/src/commonMain/kotlin/io/github/mee1080/umasim/race/calc2/SkillChecker.kt)은
코스 거리의 절반 이후에 있는 오르막을 대상으로 하며, 경사가 절반 지점을 걸치면 그 지점에서 자른다.
[원본 플레이어의 진화 스킬 설명](https://www.orooroktgameblog.net/entry/2024/07/10/123834)도
레이스 후반의 오르막 조건으로 설명하고 교토3000/3200의 활용을 다룬다.

현재 데이터에서 이 조건을 쓰는 실제 스킬은 `103003111 山頂でイタダキマス`다.
이번 데이터의 영향 대상이 하나라는 사실은 이름별 예외를 정당화하지 않는다.
같은 조건을 쓰는 향후 스킬도 공통 규칙으로 처리해야 한다.

나카야마3600에서 추첨4096개 중 **1743개가 레이스 전반의 오르막**에 배치됐다.
레이스 후반만 허용하는 비교 구현에서는 전반 추첨이0개였다.

분포 변경 효과와 혼동하지 않도록, 아래 비교에서는 현재 길이 비례 추첨·효과·물리·전개를
그대로 유지하고 **후반 영역 조건 한 군데만** 바꿨다. 변경본은 감사용 `.cache` 안에만 생성했다.

## P2: 경계에서 발동 조건과 발동 상태의 구간이 다름

[주행 코드](../assets/solo.mjs)의 발동 횟수와 지능 속도 효과 보정은 `state.phase`를 사용한다.
v9의 공간 조건은 구간에 대해 이동 전 위치를 사용하지만, 이 상태값은 이동 후 위치에서 갱신한다.
고정한 [umasim 구간·발동 집계](https://github.com/mee1080/umasim/blob/e9bb2939ba117ea93e556790c353ed3edec27eab/race/src/commonMain/kotlin/io/github/mee1080/umasim/race/calc2/RaceState.kt)는
이동 시작 위치의 같은 구간 문맥을 조건·발동 집계·지능 보정에 사용한다.

재현 입력은 주쿄1800, 선입, 순위5 고정·걸림0이다. 중반 두 번을 만드는 단순 감사용 스킬에
실제 `100591 彼方、その先へ…`와 `201611 尻尾上がり`를 붙였다.
저편은 `1199.8976 → 1200.0992m`인 프레임에서 중반 조건을 만족해 발동한다.
현재는 이를 종반 발동으로 집계해 중반3회가 되지 않으며 꼬리 올리기가 누락된다.
같은 프레임 시작 구간으로 집계하면 기존 호출 순서를 유지하면서 꼬리 올리기가 발동한다.

기본 능력치에서는 발동 이벤트가3→4개가 돼도 완주 시간은 같다.
추가 입력 `1400/2000/2500/1000/1500`, 적성A/A/A에서는
`85.25343457 → 85.24601476초`로 약0.00742초 달라졌다.
모든 경계 누락이 큰 마신 손실을 낸다고 확대 해석하지 않는다.

지능 보정도 같은 구간 불일치가 코드상 존재한다. 감사용 금색 속도 효과로 경계 발동을
재현했으나 이 입력에서는 완주 시간 차이가 없었다. 실제 특정 스킬의 성능 오류 크기는 미확정이다.
구간 문맥을 명시적으로 통일하고 후속 횟수 조건까지 검사해야 하는 공통 문제다.

## 공개 구현 사이의 차이

공개 소스는 공식 게임 사양이 아니다. 기존 v9 보고서의 추첨 근거를 다음처럼 보완한다.

### 교토 왕수: 단순 코스 금지의 근거는 부족

두 공개 코스 데이터 모두 최종 코너 시작은1395m다. 왕수는 종반·최종 코너·잔여600m 이상·순위 조건을 갖는다.
잔여거리 정수화까지 포함하면 현재 판정 구간은 약1395~1401m다.
이 스킬 조건에 **추월 중 조건은 없다**. 좁은 거리 구간을 임의의 추월 성공률로 감점해서는 안 된다.
GameWith의 약1440m 그림은 대략적인 위치 설명이므로 정확한 코스 좌표의 반증으로 쓰지 않았다.

선행에서 내리막 달인 계열의 금색 가속 `201341 決意の直滑降`를 기준으로 확보하면
왕수의 추가 기여는 **0.997→0.562마신**으로 줄었다.
실제 육성 공략의 능력치 `1850/1400/1700/1400/1300`로는 **0.856→0.448마신**이었다.
따라서 단독 표의 약1마신을 그대로 최종 조합 기여로 읽으면 안 된다.
현 물리 가정이 이 늦은 가속을 실제보다 높게 평가하는지는 독립 주행 비교가 더 필요하다.

### 육박하는 그림자: 공략과의 차이는 남음

나카야마3600은 종반2400m, 최종 직선2475m여서 가속이75m 늦다.
초기 공략은 효과가 매우 낮다고 보지만 현재 모델은1.038마신을 계산했다.
이 입력은 HP 충족 비율0이므로 회복2개와 스태미나3000 통제도 확인했다.
회복2개에서는2.169마신·HP0.938, 스태미나3000에서는2.440마신·HP1.000이었다.
HP 부족만으로 이 차이를 설명할 수 없다.
도쿄2000에서도 해당 스킬은0.794마신으로 공략의 무효 평가와 차이가 있다.
이는 **미해결 수치 검증 항목**이다. 공략에 맞춰0으로 만드는 예외를 넣지 않았다.
단독 가속의 잔여 기여·실제 다른 가속 조합·파워와 스퍼트 물리를 함께 대조할 필요가 있다.

## 실행 결과와 재현

이번에 기존 관련 Node117항목·Python51항목이 통과했다. 데이터 검증·페이지 생성·감사 코드 문법 검사도 통과했다.
기존 엔진 커밋의 [전체 CI](https://github.com/seraveist/umaBoard/actions/runs/44232769289)는 Node277·Python51 통과 기록이다.
그 기록은 회귀 방지를 뜻하며 위 새 반례의 부재를 뜻하지 않는다.
데이터 경고5개와 기존 초상 이미지 미확보 상태는 그대로이며 이번 알고리즘 감사와 별개다.

재현 도구: [audit_cm_v9_reliability.mjs](../scripts/audit_cm_v9_reliability.mjs).

```powershell
node scripts/audit_cm_v9_reliability.mjs --mechanics
node scripts/audit_cm_v9_reliability.mjs --races
node scripts/audit_cm_v9_reliability.mjs --extra --followup --oracle
```

감사용 비교 모듈은 `.cache/v9-reaudit`에 생성된다. 운영 `assets`를 덮어쓰지 않는다.
`--oracle`은 `--extra` 결과가 필요하다. 별도 경사 비교는 pinned umasim 정책의 민감도이며 게임 정답 판정기가 아니다.
`phase_firstquarter` 직접 판정도 의도한 공간 의미를 검사하며 Kotlin 구현 전체를 그대로 실행한 것이 아니다.
무작위 비교 중 `200511 全身全霊`는 직선 무작위 스킬이 아니라 무변화 대조군이다.
실제 직선 무작위 비교는 추가 결과의 `200362`, `200372`로 구분한다.
