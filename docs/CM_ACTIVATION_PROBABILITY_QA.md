## 1. 결론과 검증 범위

자기 발동 조건을 지워 모든 스킬이 성공한 것으로 계산하던 문제를 공통 주행 모델에서
수정했다. 마신표와 최종 추천은 같은 조건 판정·확률 추출·HP 주행·비교기를 사용한다.
특정 스킬ID를 막거나 점수를 덮어쓰는 보정은 추가하지 않았다.

다만 상대 8명의 주행까지 계산하는 모델은 아니다. 미입력 순위·추월·간격 등은 여전히
조건 충족을 가정한다. 따라서 결과는 **자기 조건과 확률을 반영한, 명시된 상대 조건하의
단독 기여**다. 실제 전체 발동률·승률·게임 재현 오차가 검증됐다는 뜻은 아니다.

## 3. 모델의 근거와 적용 방법

### 발동 판정

- 원본 `activation_raw=0`은 지능 판정 면제다. 그 외에는
  `max(0.2, 1 - 90 / 표시 지능)`을 스킬별 한 번 추출한다.
  원본 메타데이터가 없는 검토된 본체 고유 보충분은 고유기 등급의 면제 정책을 사용한다.
  지능3000에서도 일반 스킬을100%로 만들지 않는다.
- `random_lot==p`는 별도 `p/100` 추첨이다. `random_lot_shared`는 같은 스킬의
  인기 분기들이 하나의 추첨을 공유한다. 위치 추첨·효과량 추첨·지능 판정은 별도 채널이다.
- 게이트·인기를 알고 있으면CM9의1~9를 입력한다. 미입력 게이트는 균등 추출하고,
  인기는 균등 사전가정을 사용한다. 인기 분포는 실측된 분포로 주장하지 않는다.
- 발동 횟수 조건은 실제 발동 이벤트, 회복 조건은 실제 양수 회복에서 증가한다.
  계승 수는 보유 개수이므로 발동 실패/고정 조건 비활성 여부와 구분한다.
- 동일 스킬의 대체 분기는 같은 공간 추첨을 공유한다. 강화 분기와 기본 분기가
  별도로 주사위를 굴려 기본 효과가 먼저 발동하는 오류를 막는다.
- 명시된 숫자 외부 조건과 거리순 순위 기록은 `raceContext.conditions` /
  `raceContext.rankTimeline`으로 평가할 수 있다. UI에는 게이트·인기만 노출한다.

### HP와 조합 탐색

공개HP 모델의 종반60m 거리 예산을 사용한다. 최대 속도로 남은 거리를 감당할 수
있으면 즉시 최속 스퍼트를 선택한다. 부족하면 종반 기본 속도와 후보 속도0.1m/s 간격의
거리 분할을 비교한다. 지능에 따른 후보 수용 판정도 별도 표본을 사용한다.
계획에 미래 회복을 미리 더하지 않는다. 이미 발동한 회복만 HP를 갱신하고 재계획한다.

근거: [alpha123 HpPolicy](https://github.com/alpha123/uma-skill-tools/blob/bce6c08/HpPolicy.ts),
[umasim calcSpurtParameter / calcSpurtDistance](https://github.com/mee1080/umasim/blob/e9bb2939ba117ea93e556790c353ed3edec27eab/race/src/commonMain/kotlin/io/github/mee1080/umasim/race/calc2/RaceCalculator.kt).
게임 내부 모델 전체의 정확성을 보증하는 공식 수식은 아니다.

탐색에서는 모든 표본의 최속 스퍼트 충족, 미충족 시 표본 충족률과 평균 부족량,
평균 마신, 비용 순으로 비교한다. 모든 조합의 전역 최적성을 주장하지 않는다.
보조 묶음은 조건식에서 일반적으로 유도하며 필요 개수3개 이하의 일부 조합과
추가 보조자0~2개를 비교한다. 가능한 모든 보조 조합을 전수 조사하는 것은 아니다.
최종 정밀 단계는 추가·승급·삭제·시나리오 진화 조합을 다시 검사한다.

수식·판정·평가의 소유 모듈은 `activation.mjs`, `race-sampling.mjs`, `solo.mjs`,
`spurt-planning.mjs`, `race-evaluation.mjs`, `skill-dependencies.mjs`다.
1차와 최종 단계의 구현을 따로 분기해 같은 조건이 다르게 계산되던 구조를 피했다.

## 5. 자동 검증과 재현

`tests/cm-activation-probability.test.mjs`는 임의ID·여러 임계값을 사용해
추첨0/15/30/50/60/100%, 공유 추첨, 지능 면제, 회복/소유/HP/계승 조건,
알려진 순위/외부값, Top10 밖 비활성 보조 계승의 실제 최종 추천을 검사한다.
58개 실제 자기 조건 레코드의 조건 보존도 확인한다.

거리 예약 최적화와 매 프레임 전체 조건 검사 결과를32표본에서 비교해
이벤트·HP·도착 시간이 동일함을 확인한다. HP 계획의 거리/예산 보존과
HP 부족 시 스퍼트 판정/도착 시간 변화도 검사한다.
저장 키 호환 검사는 확률 입력 변경 후에도 획득 기록이 남는지 확인한다.

재현 명령(저장소 루트, Node24/Python3.12+):

```sh
node --test tests/*.test.mjs
python -m unittest discover -s tests -v
python scripts/validate_data.py
python scripts/build_pages.py
node scripts/validate_cm_model.mjs
```

마지막 명령은 과거v5 고정 입력을 읽어 최신 검증JSON을 다시 만들며,
추첨 기대율·자기 조건·충돌·표본 수렴·예산·최종 후보 추가 검사 완료를 검증한다.
최종 로컬 검증: **Node227개 + Python51개 =278개 통과**. 데이터 검증 통과
(기존 경고5개), 정적 페이지 빌드·전체 브라우저 모듈 구문 검사·공백 오류 검사 통과.
UI 규칙의 strict 정적 감사는 오류/경고0개다. 복제 환경에는 초상화 캐시가 없어
빌드에서 기존 이름 대체 표시를 사용했다. 데이터/아이콘 원본은 변경하지 않았다.
최종 비교 규칙 정리 후 CM118개를 다시 통과했고, 알려진 외부값의 즉시 판정과
UI 계약을 포함한 집중23개 검사도 통과했다. 표본 확대는 연산량을 늘린다.
계산은 기존 취소 가능한Worker에서 수행하며, 짧은 표본으로 정확성을 보장한다고 주장하지 않는다.

브라우저 자동 검증은 인앱 브라우저의 로컬 서버 연결 실패 후 Windows Chrome을
시도했으나 도구가 현재 주소를 안전하게 확인하지 못해 중단했다.
이번 변경의 실제 데스크톱/모바일 화면 검증은 완료하지 못했다.
정적 UI 계약 검사와 빌드 성공을 시각/키보드/터치 실기기 검증으로 대체 주장하지 않는다.

## 6. 남은 한계와 다음 우선순위

1. 상대 주행이 없는 순위·추월·간격·팀 조건은 여전히 조건부다. 근거 없는 일괄 발동률을
   새로 만들지 않았다. 실제 관측 전개를 넣거나 다주자 모델로 확장해야 전체 확률을 다룰 수 있다.
2. 속도2000초과 전개 스퍼트는 공개 추가 가속 근사이며 미확정 상한을 유지했다.
   [공개 시뮬레이터 작성자의 한계 설명](https://note.com/uma_analysis66/n/n0a19b02bf4f3)도
   불확실성을 밝힌다. 임의 상한을 넣어 정확한 값처럼 만들지 않았다.
3. HP 계획은 공개 거리 예산을 사용하며 블로킹·내리막 모드·상대 소비·모든 가속/일시
   속도 효과를 미리 아는 완전한 게임 계획기가 아니다. 실측 여러 거리/스태미나/회복과 대조가 남는다.
4.128표본 결과와 반별 차이는 통계적 보장이나 신뢰구간이 아니다. 근소한 순위는 seed/
   표본 확대 검증이 필요하다. 탐색의 짧은8표본과 제한된 보조 묶음은 전역 최적성을 보장하지 않는다.
5. 진화 해금은 기존 사용자 입력/후보 제외 기능에 의존한다. 게임에서 달성하지 못한
   진화는 제외해야 한다. 이번 수정은 진화 해금 자동 판정기를 구현한 것은 아니다.
